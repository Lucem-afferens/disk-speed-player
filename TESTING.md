# Проверки перед публикацией

Дата: 15 ноября 2026 года. Проверки выполнены на Mac; пользовательские ссылки, видео и снимки кадров не включены в репозиторий.

После публикации сценарии повторены на [публичном HTTPS-адресе GitHub Pages](https://lucem-afferens.github.io/disk-speed-player/): оба мобильных профиля, длинная запись, перемотка, Range и адаптивные макеты прошли проверку. Локальный сервер для этих проверок не использовался.

## Автоматические проверки

- 20 модульных тестов: публичные ссылки, вложенные Unicode-пути, изоляция истории, ограничения источников, fallback скорости, отсутствие скачков после буферизации, валидация MP4 и HEVC-конфигурации.
- Синтаксис всех JavaScript-модулей и Service Worker проверен Node.js.
- Макеты шириной 320, 390, 844 и 1440 пикселей: нет горизонтального переполнения, меню скорости помещается на экране.

## Прямое подключение к Яндекс Диску

На настоящей публичной папке из 73 видео проверены список, получение временной ссылки и ответы HTTP 206 на диапазоны байтов. Использованы короткая HEVC-запись 1920×1080 и запись длительностью около 20 минут.

В двух автоматизированных мобильных профилях также проверены: изменение скорости внутри развёрнутого плеера рядом со звуком, отметка просмотра, сохранение отметки и скорости после перезагрузки, фильтрация плейлиста. Необработанных JavaScript-ошибок не обнаружено.

## Границы проверки

Мобильный профиль браузера на Mac **не заменяет физический iPhone или Android**: аппаратные декодеры, доступ к сети, память и расход батареи отличаются. Физические устройства не были подключены. Плавное 32× на любом телефоне не гарантируется. Особенно важна проверка HEVC на конкретной модели Android; если аппаратного декодера нет, исправление контейнера не добавит его.

Для проверки на своём телефоне: открыть публичную страницу, вставить ссылку, запустить видео, выбрать 2× / 16× / 32×, развернуть плеер, перемотать к середине, поставить отметку просмотра и перезагрузить страницу. При недостатке сети плеер должен явно показывать снижение скорости.

## Исправление Safari — версия 20261115.2

Воспроизведена последовательность «первое открытие работает, повторное — ошибка»: до активации Service Worker запрос Range получал 206 и 16 байтов. После активации воркера тот же запрос получал 200 и полный файл, включая запрос с уникальным адресом и `cache: no-store`. Значит, причиной в этом воспроизведении был не кэш: WebKit терял Range при неявной передаче запроса через воркер. Старый код чтения заголовка отклонял 200, а интерфейс маскировал это сообщением о формате.

Исправление явно передаёт исходные запросы диапазонов Яндексу через `respondWith(fetch(event.request))`. Новый воркер активируется до первого чтения заголовка, чтобы работало обновление со старой версии. В контрольном сценарии все три запроса после исправления возвращают 206 и 16 байтов. Формат видео не менялся. Это точная причина воспроизведённого сбоя на WebKit; журнал физического iPhone пользователя недоступен.

Воспроизведён дефект прежнего воркера: после потери памяти и при внутреннем `clientId` медиазапроса, который не соответствует окну, восстановление не опрашивало другие вкладки и возвращало 410. Интерфейс при этом мог показать сообщение о формате. Это дополнительный дефект восстановления потока, исправленный в том же обновлении.

Добавлены регрессионные проверки: перезапуск воркера без исходной вкладки, неизвестный `clientId`, восстановление из хранилища, диапазон внутри заменяемой метки, корректный укороченный Range, обновление ссылки после 403, диагностика 429, неверные диапазоны и недопустимые источники.

Браузерные проверки выполняются с настоящими данными Яндекс Диска. Проверка вызова системного полноэкранного API подменяет сам API, поскольку WebKit на Mac не предоставляет интерфейс физического iPhone. Режим standalone для проверки геометрии также моделируется; установка с экрана «Домой» на физическом устройстве этим не подтверждается.

Проверено на локальной версии: обновление с ранее опубликованного коммита (новый воркер активируется, HEVC снова играет); полное закрытие и запуск WebKit с прежним профилем (старый поток восстанавливается из IndexedDB без исходной вкладки); повторное открытие ссылки; вызов native fullscreen; макеты standalone 390×844 → 844×390 → 390×844, без переполнения, со скоростью рядом со звуком.

Принудительная ошибка 429 на первом чтении заголовка отображается как ограничение запросов, с HTTP-статусом в локальной диагностике. После снятия ограничения кнопка повтора открывает настоящую длинную HEVC-запись. В горизонтальном развёрнутом режиме название и управление наложены поверх изображения, чтобы панели не уменьшали высоту видео.


## Смена источника и очистка — версия 20261115.3

До исправления `loadSource()` оставлял прежнее видео открытым до загрузки первого видео нового источника. При пустой папке или ошибке API старый ролик вообще не закрывался. Кнопка истории оставляла текущий поток и плейлист, а события плеера могли снова записать очищенные позиции.

Теперь смена источника сначала сохраняет позицию, отменяет прежние запросы, освобождает видеоплеер и сбрасывает список. Поколение сессии отсекает поздние ответы и восстановление Safari. Полная очистка дополнительно удаляет описания потоков из памяти/IndexedDB, отменяет передачу тела ответа, обновление временного адреса и чтение метаданных; при ошибке хранилища успех не показывается. Вкладки получают единое событие сброса без повторной отмены новой сессии.

Проверено локально 15 ноября 2026 года:

- 28 модульных тестов, включая поздний ответ вкладки, позднее обновление адреса, незавершённую запись IndexedDB, отмену активного тела ответа и ошибку очистки.
- `npm run test:browser`: Chromium / Pixel 7 и WebKit / iPhone 13. Переход A → B с одинаковыми путём и размером файла, пустая папка, HTTP 404, устаревший ответ, очистка незавершённого запроса списка/видео, сохранение истории по умолчанию, удаление истории по выбору, сброс двух вкладок, пустое IndexedDB и отсутствие восстановления после перезагрузки. Проверена ширина 320, 390 и 844 px.
- Настоящая HEVC-запись 1920×1080 с Яндекс Диска воспроизвелась в Chrome напрямую и в WebKit через совместимый поток. Цикл «просмотр → очистка → открытие той же ссылки → просмотр» прошёл в обоих браузерах без ошибок JavaScript.

Физический iPhone не использовался; мобильный профиль WebKit на Mac не подтверждает поведение всех версий iOS.
